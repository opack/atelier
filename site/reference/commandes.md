# Commandes

## Commandes Claude Code

atelier est un plugin Claude Code : ces commandes se lancent **dans une session Claude Code ouverte sur le répertoire du projet**, pas dans un terminal.

| Commande | Étape | Rôle |
|---|---|---|
| `/atelier:init` | Projet | Installe atelier : contrôles, dossiers, section Process du `CLAUDE.md`, déclaration du plugin. Relancée sur un projet installé : propose d’ajouter les lignes de la section Process qui manquent. |
| `/atelier:new [type] [source]` | Intention | Ouvre un chantier : identifiant (après `git fetch`), branche, dossier, spec construite en questionnant les manques, décision TDD (sauf EPIC), relations si le contexte en suggère, commit et push du brouillon (qui réserve l’identifiant). Propose un EPIC pour une demande à plusieurs livrables. |
| `/atelier:sign [modèle] [effort]` | Signature | Complétude, relecture critique, signature sur votre confirmation explicite. Le modèle et l’effort du sous-agent `spec-critic` peuvent être donnés en argument pour cet appel. |
| `/atelier:plan` | Conception | Approche, fichiers, tranches → `plan.md` ; décisions → `decisions.md`. Pour un EPIC : le découpage en chantiers (`plan-epic`). |
| `/atelier:amend <changement>` | Après signature | Modifie la spec signée : entrée datée, impact sur les critères, votre nouvel accord, commit. |
| `/atelier:write-tests [raison]` | Tests d’abord | TDD étapes 1 à 3 pour la tranche en cours : tests de ses CA, échec vérifié, relecture, commit, gel. Relancée avec une raison : rouvre des tests figés (de la tranche, ou d’une tranche précédente), raison tracée. |
| `/atelier:build [modèle] [effort] [tranche]` | Implémentation | TDD étapes 4 et 5 (ou implémentation simple sans TDD) pour la tranche en cours : le sous-agent `implementer` écrit le code jusqu’au vert, vérification du surapprentissage, commit après validation. Le modèle et l’effort d’`implementer` peuvent être donnés en argument pour cet appel. L’ordre des mots est libre. L’argument de tranche ne sert qu’au `SPIKE` sans TDD ; ailleurs, un numéro de tranche est ignoré, et tout autre mot (modèle ou effort mal écrit) fait arrêter la commande. |
| `/atelier:review [modèle] [effort]` | Revue | Revue de la tranche en cours, puis revue du chantier après la dernière : contrôles, revue indépendante, traitement des points, autant de revues que nécessaire, `revue.md`, votre validation, passage à la tranche suivante ou commit revu enregistré. Le modèle et l’effort du sous-agent `reviewer` peuvent être donnés en argument pour cet appel. |
| `/atelier:close` | Clôture | Toutes les tranches revues, revue du chantier à jour (sauf SPIKE sans TDD et EPIC sans branche d’intégration ; revue d’ensemble pour un EPIC à branche d’intégration), dépendances livrées, enfants d’un EPIC clos, `bilan.md`, verdict, vérifications déterministes, proposition de PR. |
| `/atelier:status` | Toutes | Chantier actif, statut, tranche en cours, phase TDD, état de la revue, relations, prochaine étape. |
| `/atelier:off <raison>` | Urgence | Débrayage : code autorisé sans spec, tracé. |

## Ligne de commande `atelier`

Utilisée par les commandes `/atelier:*` et par les hooks : l’agent la lance pour vous. C’est le seul moyen prévu de modifier l’état d’un chantier (statut, signature, TDD après signature, gel des tests, revue) : les outils d’édition de l’agent ne le peuvent pas.

| Commande | Rôle |
|---|---|
| `atelier status [--json]` | État du chantier actif, dont la tranche en cours (`slice` : numéro ou `"chantier"`, `sliceCount` : nombre de tranches du plan ; `null` pour un chantier à tranche unique ; `sliceTdd` : TDD déclaré de la tranche, `yes`, `no` ou `null`), l’état de la revue (`reviewedCommit`, `reviewState` : `none`, `current` ou `stale`), `codeCommitted` (du code a-t-il été commité depuis le début de la tranche, ou depuis le gel des tests en TDD : `true` ou `false` ; `null` quand ce n’est pas calculé, faute d’effet sur la prochaine étape, ou incalculable), ses relations (parent, dépendances, origine, remplacement, enfants d’un EPIC, avec leur statut dans la branche courante) et sa base (`baseBranch` : la branche d’intégration de l’EPIC qui l’impose, nommé dans `baseEpic`, sinon la branche par défaut, `null` si elle est inconnue). |
| `atelier base --parent <ID>` | Base d’un chantier à ouvrir sous le parent `<ID>` : la branche d’intégration de l’EPIC à branche d’intégration le plus proche en remontant les parents, sinon la branche par défaut. Lue par `/atelier:new` pour choisir le point de départ de la branche ; fonctionne depuis la branche par défaut, où la spec de l’EPIC n’existe pas encore. Voir [EPIC à branche d’intégration](../fondations/types#epic-a-branche-d-integration). |
| `atelier next-id <TYPE>` | Prochain identifiant du projet. Le compteur est commun à tous les types et suit le plus grand numéro trouvé dans les dossiers de chantier, les identifiants en tête de segment des noms de branche (`fix/BUG-421-x`) et les identifiants entre crochets des sujets de commit (`[FEAT-7]`) : un `CA-13` ou un `UTF-8` dans la prose d’un commit ne compte pas. |
| `atelier template <nom>` | Affiche un template (`spec-feat`, `spec-epic`, `plan`, `plan-epic`, `process`, `bilan`…). |
| `atelier check-spec <fichier>` | Liste ce qui manque dans une spec, relations comprises (identifiants connus, parent EPIC unique et ouvert, ni auto-référence ni cycle). |
| `atelier check-process` | Liste les lignes de la section « Process (atelier) » absentes du `CLAUDE.md` du projet. |
| `atelier check-plan [chemin du plan]` | Vérifie le plan : numérotation, TDD non déclaré, `TDD : oui` sans critère, critères absents de la spec ou couverts par aucune tranche. Sortie 0 sans problème, 2 avec des problèmes listés, 1 en cas d’erreur ; un EPIC est ignoré. Pour le `plan.md` du chantier, écrit `slice_tdd` d’après la tranche 1 seulement tant que `slice_tdd` est vide et que la tranche 1 n’a ni tests figés ni revue. |
| `atelier sign` | Signe la spec du chantier actif. Refuse si elle est incomplète ou n’est pas en brouillon. |
| `atelier set-tdd <yes\|no> [raison]` | Enregistre la décision TDD, tracée après signature. `yes` est refusé sur un EPIC. Dans un chantier en tranches, ne change que la tranche courante (`slice_tdd`) ; refusée si les tests de la tranche sont figés, et `no` refusé pendant une réouverture. |
| `atelier freeze-tests` | Fige les tests commités (TDD) ; écrit `slice: 1` au premier gel ; trace le regel après une réouverture. Refusée si une ligne d’un test d’une tranche précédente a été modifiée ou supprimée sans réouverture, ou si `slice_base` n’est plus un ancêtre de `HEAD`, ou dans une tranche `TDD : non`. |
| `atelier reopen-tests <raison>` | Rouvre les tests figés, raison tracée ; aussi les tests des tranches précédentes, en phase « tests d’abord » d’une tranche N > 1. Refusée si la spec n’est pas signée, sans TDD ou dans une tranche `TDD : non`, si rien n’est figé (tranche 1) ou si les tests sont déjà rouverts. Possible en revue d’ensemble si une tranche a figé des tests. |
| `atelier tests-changed` | Liste les tests modifiés depuis leur gel : non commités, ou modifiés par le chantier (ses commits et la résolution de ses fusions). Les lignes apportées par une fusion de la branche par défaut, conflit compris, ne comptent pas ; une ligne figée modifiée ou retirée compte. |
| `atelier checks [--force]` | Lance les contrôles configurés, sauf s’ils sont déjà verts sur l’état actuel du code (fichiers non commités compris) : il le dit et ne les relance pas. Ce résultat est partagé avec `close-check`, `set-status done` et le contrôle de fin de tour. `--force` relance quand même, par exemple après un changement que git ne voit pas (fichier ignoré, version de Node). |
| `atelier review-ids [--json]` | Prochains numéros des points de relecture du chantier actif, un par préfixe (`RB`, `RD` : revue de code, lus dans `revue.md` ; `SB`, `SD` : relecture de spec, `OB`, `OD` : surapprentissage, lus dans `spec.md` et `decisions.md`), et les points de revue ouverts, dont la dernière occurrence n’a pas de traitement (identifiant, intitulé, section). Sans fichier : tous les numéros à 1. Les commandes `/atelier:*` passent ces numéros aux sous-agents. |
| `atelier set-reviewed` | Après votre validation de la revue : passe à la tranche suivante (`slice`, `slice_base`), ou à la revue du chantier après la dernière (`slice: chantier`, `last_slice`) ; pour la revue du chantier ou un chantier à tranche unique, enregistre le commit revu (`reviewed_commit`). Refusée sans spec signée, avec du code ou une spec non commités, en TDD si les tests ne sont pas figés ou ont changé, pour une tranche vide, si `slice_base` n’est plus un ancêtre de `HEAD`, ou si `revue.md` (copie de travail) a un problème : point sans traitement reconnu, mal formé ou mal rangé, identifiant en double, renvoi manquant (voir [Revue](../cycle/revue#_4-consigner-valider-passer-a-la-suite)) ; elle liste alors ces problèmes. |
| `atelier close-check` | Vérifie que le chantier peut être clôturé : toutes les tranches du plan revues et revue du chantier à jour (sauf SPIKE sans TDD et EPIC), travail commité, tests figés en TDD, contrôles verts, dépendances `done` dans la branche courante, aucun point de `revue.md` ouvert (sans traitement, ou encore `reporté (tranche N)`) ni autre problème de `revue.md` (voir [Revue](../cycle/revue#_4-consigner-valider-passer-a-la-suite)), et `revue.md` commité (sauf SPIKE sans TDD et EPIC) ; pour un EPIC, enfants tous clos dont au moins un `done`. |
| `atelier set-status <statut>` | Passe le chantier en `draft`, `done` ou `abandoned`. La signature ne passe que par `atelier sign`. Une spec non brouillon ne repasse pas en `draft` ; `done` refait les vérifications de `close-check`. `abandoned` sur un EPIC liste ses enfants encore ouverts, sans cascade. |
| `atelier agent-settings <agent> [--user-model <v>] [--user-effort <v>] [--args <argument>]` | Résout le modèle et l’effort d’un sous-agent (argument > option > valeur recommandée) et rend le résultat en JSON : modèle, effort, origine de chaque valeur, `rest` (le reste de l’argument) et avertissements. Refuse deux modèles ou deux efforts différents dans l’argument, un sous-agent inconnu et une option répétée. |
| `atelier bypass on <raison>` / `off` | Active ou lève le débrayage. |
| `atelier hook-guard`, `hook-gate`, `hook-session-start` | Réservées aux hooks, voir [Hooks et configuration](./configuration). |

## Sous-agents

| Sous-agent | Quand | Rôle |
|---|---|---|
| `spec-critic` | Avant signature | Relit la spec sans voir la conversation : ambiguïtés, cas limites, critères invérifiables. Points `SB1`… (bloquants), `SD1`… (à discuter). |
| `implementer` | `/atelier:build` | Écrit le code de la tranche jusqu’au vert, sans toucher aux tests, et ne commite pas. S’arrête par « Arrêt : test à revoir » si un test lui semble faux. |
| `overfit-checker` | Après le passage au vert | Vérifie que le code résout la spec et ne surapprend pas les tests. Points `OB1`…, `OD1`…. |
| `reviewer` | À chaque revue, jusqu’à ce que chaque point ait un traitement | Points `RB1`…, `RD1`…, numérotés sur tout le chantier ; reprend un point encore ouvert sous son identifiant. Revue de tranche en huit dimensions, ligne à ligne ; revue du chantier transversale (couverture des CA, cohérence entre tranches, restes, écarts) ; revue d’ensemble d’un EPIC à branche d’intégration (cohérence entre lots, CA globaux, résolutions de conflits). Ne modifie rien. |

Le modèle et l’effort recommandés de chaque sous-agent, et leur ordre de résolution, sont décrits dans [Modes de travail](../agent/modes).
